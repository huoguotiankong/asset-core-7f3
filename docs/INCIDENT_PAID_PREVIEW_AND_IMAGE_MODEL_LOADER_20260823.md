# 收费试看误判与自定义图片 ModelLoader 事故（2026-08-23）

## 背景
汤头条 APK 9.6.2 的实机恢复过程中出现两个高度可复用的错误判断：

1. 长视频详情下发的媒体可以技术上正常播放，但只有数秒维护片或约 120 秒试看；如果只按播放器是否能打开判断，会把业务访问控制误诊为播放故障。
2. 原 APP 注册了自定义 Glide `String -> InputStream` ModelLoader，内部自行生成图片候选、逐个发请求、落盘/判型、必要时解密。把它简化成“远程 URL 先由海阔下载成功，再在 `@js` 回调解密”时，某些图片会永远进不了真正的解密阶段。

## 1. 收费/试看首先是业务访问状态，不是媒体故障
当 APK/官方客户端模型存在：

```text
isfree
coins
is_pay
preview_tip
preview_video
```

应先恢复业务语义，再决定播放器行为。

汤头条已逆向确认：

```text
isfree != 0
→ 免费 / 无限看

isfree == 0 && coins > 0 && is_pay == true
→ 已购买

isfree == 0 && coins > 0 && is_pay == false
→ 未购买收费视频
```

未购买状态下，详情里的 `source_*` 可以是升级提示/占位源，`preview_video` 可以是限定时长试看。此时不应继续通过自动换画质、嗅探或阈值放宽来“找完整源”。

## 2. 购买/解锁接口属于有副作用操作
汤头条 APK 已确认：

```text
POST /api/user/watchingMvByCoins
payload: { mvId }
response data: VideoShopBean { code, msg, url }
```

成功后 `url` 才是客户端用于完整播放的地址。

固定安全规则：
- 页面加载、预检、自动回退、后台诊断绝不能调用购买接口。
- 必须由用户显式点击“解锁/购买”。
- 调用前必须再次明确确认价格/消耗。
- 余额不足、登录要求、业务失败必须原样提示，不能伪成功。
- 不尝试绕过官方付费/授权控制。

## 3. 自定义 ModelLoader 不能只复制最终解密算法
原 APP 的图片链如果是：

```text
原始字段
→ 生成多个候选 URL
→ Loader 自己逐个请求
→ 空响应/坏响应则下一个候选
→ 缓存/字节判型
→ 已是 JPEG/PNG/WebP 等则直接返回
→ 非图片字节再尝试自定义解密
```

则海阔端也应尽量保留这个边界。单纯：

```text
远程 URL
→ 海阔图片加载器
→ @js 回调
→ 解密
```

存在一个前提：远程响应必须先被海阔图片加载链接受。若原服务的响应头、字节形态或错误重试行为与普通图片不同，回调可能根本没有获得原 APP Loader 能处理的字节。

可采用：

```text
稳定本地占位图片触发 image JS
→ JS 内部主动 fetch(realUrl, {toHex:true})
→ 多候选 / 多 Header 模式重试
→ magic 判型
→ legacy AES-CFB / AES-CBC 等转换
→ ByteArrayInputStream
```

这样真正的网络获取、重试和解密职责都回到 ImageAdapter，而不是被宿主图片预取链截断。

## 4. 图片诊断要求
至少记录：
- 候选序号；
- 使用的 Header 模式名称，不记录 Cookie/Token 明文；
- 输入/输出字节数；
- `plain / legacy-cfb / aes-cbc`；
- 最终图片类型；
- 失败时最近若干候选/模式错误。

## 5. 固定回归
涉及同类 App 时至少分别验证：
- 免费短视频封面；
- 长视频/付费视频封面；
- 头像/漫画图片等其它图片域；
- 免费完整视频；
- 已购视频；
- 未购视频的试看；
- 未购视频不会在任何自动流程中触发消费。
