# 海阔程序名与正式版 / 测试版 / 本地版通道规范

版本：1.2  
日期：2026-08-21  
适用范围：本项目所有海阔首页频道、小程序、云仓库多版本入口与 GitHub 远程发布。

## 0. 开发前强制阅读

每次开始开发、修改、发布任意海阔小程序前，必须先读取 GitHub `main` 分支当前最新的长期三文档：

1. `docs/PROJECT_PLAN.md`
2. `docs/HIKER_APP_DEVELOPMENT_GUIDE.md`
3. `docs/HIKER_APP_DEVELOPMENT_CAUTIONS.md`

涉及 Stable / Test / Candidate / Beta / Dev / Local、规则命名、覆盖安装或云仓库版本通道时，在三文档之后还必须读取本文件 `docs/HIKER_RULE_NAME_CHANNEL_POLICY.md`；涉及版本号先后关系、Stable 晋级后 Test 如何续线、Local 从哪个版本派生时，还必须遵守 `docs/VERSION_CHANNEL_GOVERNANCE.md`。

不得依赖旧对话里的记忆版本代替读取。文档与旧实现冲突时，优先遵守当前 GitHub 文档；实机验证结果需要形成长期规则时，应同步回写文档。

## 1. 核心事实

海阔以**程序 / 规则名称**判断导入内容是否属于同一个程序。同名导入会覆盖原程序；名称不同则会作为两个程序分别存在。

因此，程序名不是纯展示字段，而是发布与覆盖安装语义的一部分。

本项目从 2026-08-21 起统一采用三种发布形态：

```text
正式版 Stable   → 默认远程代码
测试版 Test     → 默认远程代码
本地版 Local    → 可选，纯本地完整代码
```

其中本地版不是“正式版的另一种实现”，也不再划分 Stable/Test；它是独立的第三通道。

## 2. 版本谱系：Stable / Test / Local 不能各自乱走

Stable / Test / Local 是三个发布通道，但必须属于同一个可解释的版本谱系。

### 2.1 Test 基础版本不得低于 Stable

版本比较先取数值基础版本，例如：

```text
3.5.3-rc1      → 3.5.3
3.9.41-test.1  → 3.9.41
```

硬规则：

```text
Test 基础版本 >= Stable 基础版本
```

禁止长期出现：

```text
Stable 3.5.2
Test   3.5.0-rc12
```

这种状态会造成“测试版看起来比正式版旧”，也容易让 Test 继续从旧分支开发而漏掉 Stable 后来已经合入的修复。

### 2.2 正常向前开发时 Test 应使用下一个目标版本

例如当前 Stable 为 `3.5.2`：

- patch 级修复/增强：Test 从 `3.5.3-rc1` 开始。
- minor 级功能升级：Test 从 `3.6.0-rc1` 开始。

不得继续把 `rc13 / rc14 / rc15` 堆在已经落后的 `3.5.0` 基础版本上。

### 2.3 Stable 晋级后，下一轮 Test 必须先 rebase 当前 Stable

下一轮 Test 必须继承当前 Stable 已经验证的全部能力、故障修复、Recovery、Local 支持和安全补丁，再叠加新功能。

禁止：

```text
Stable 已加入 Local / Recovery / 安全修复
Test 仍从更旧 release 派生，只保留 UI 新功能
```

Test 是“下一版候选”，不是长期平行旧分支。

### 2.4 允许同基础版本测试，但必须有明确用途

如果只是验证同一 Stable 基线的 Shell、打包、Local 构建或覆盖安装，可使用：

```text
Stable 3.9.41
Test   3.9.41-test.1
```

此时 Test 表示同基线测试构建，不表示新的产品版本。

### 2.5 Local 不参与谁新谁旧的排序

Local 是纯本地派生产物，推荐版本：

```text
3.5.2-local
3.5.2-local.1
```

推荐额外声明：

```text
baseVersion
DerivedFromChannel
DerivedFromVersion
```

Local 的修订号只表示本地打包、隐私清理或兼容调整，不代表它比 Stable/Test 更先进。

完整版本谱系规则见 `docs/VERSION_CHANNEL_GOVERNANCE.md`。

## 3. 默认规则：其它小程序正式版与测试版必须同名

除“我的规则仓库”这个自举安装中心外，同一个小程序的 Stable / Test / Candidate / Beta 等远程通道：

- Shell 内 `title` 必须保持与正式程序完全相同。
- `channels.json` 中正式版和测试版的 `name` 必须与云仓库主程序名完全相同。
- 不要在测试版程序名后追加“测试版”“Beta”“Candidate”等字样。
- 通道可以拥有不同 `id`、release、build、Bootstrap、Remote Manager state，但**用户看到并被海阔用于覆盖判断的程序名保持一致**。
- 正式版与测试版默认都采用远程代码架构；Stable 与 Test 的 release/build/cache/state 必须隔离，测试代码不得原地修改已发布 Stable release。

标准体验：

```text
云仓库
  ↓
某程序
  ↓
正式版 / 测试版 / 本地版（可选）
  ├─ 导入正式版 → 覆盖当前同名正式/测试程序
  ├─ 导入测试版 → 覆盖当前同名正式/测试程序
  └─ 导入本地版 → 以“某程序 本地版”独立存在
```

测试版如果出现问题：

```text
回到“我的规则仓库”
  ↓
找到该程序
  ↓
导入正式版
  ↓
同名覆盖恢复
```

这样避免手机里长期同时存在“某程序”和“某程序 测试版”两个远程副本，同时允许用户在需要时额外保留一个完全独立的本地版。

## 4. 本地版：独立第三通道

任何普通小程序都可以额外提供一个 Local 通道，但必须同时满足以下约束。

### 4.1 命名

本地版统一命名为：

```text
<正式规则名> 本地版
```

例如：

```text
JavDB v3        → 正式版 / 测试版共同使用的规则名
JavDB v3 本地版 → Local 规则名
```

禁止使用“Local”“离线版”“纯本地正式版”“本地测试版”等其它长期命名格式。

### 4.2 本地版不分正式与测试

Local 本身就是独立发布形态，不再继续拆：

```text
本地正式版
本地测试版
```

需要验证本地打包变化时，应先在远程 Test 中验证业务逻辑，或生成临时构建产物测试；最终云仓库只保留一个正式可用的 Local 入口。

### 4.3 必须是真正纯本地代码

本地版导入完成后的规则本体必须包含运行所需的完整业务代码，不得依赖私人远程代码运行，包括但不限于：

- GitHub Remote Module。
- 私人 Raw/CDN 模块地址。
- `latest.json` / Remote Manager 运行依赖。
- 私人升级、回退、远程补丁入口。

允许“我的规则仓库”在**导入阶段**从云端读取构建材料并一次性组装本地规则，但组装完成后的目标规则必须能够脱离私人 GitHub 独立运行。

### 4.4 本地版隐私硬要求

本地版规则源码、内嵌 pages、PrivateJS、配置和可见文本中都不得包含用户私人信息，包括但不限于：

- 用户 GitHub 用户名、仓库地址、Raw URL、API contents URL。
- 个人邮箱、手机号、真实姓名、账号 ID。
- Token、Cookie、Authorization、API Key、密码、测试账号。
- 本机 `/home`、`/Users`、`/mnt/data` 等开发路径。
- 私有服务器、Webhook、日志收集地址。
- 其它可以反推出用户身份或私人基础设施的信息。

发布 Local 前必须对**最终生成后的规则本体**做静态隐私扫描，而不是只扫描构建模板。

## 5. 唯一默认例外：我的规则仓库

“我的规则仓库”承担整个云仓库的安装、自救与版本恢复职责，因此正式版与测试版**必须使用不同程序名并允许同时安装**：

- 正式版：`我的规则仓库`
- 测试版：`我的规则仓库·测试版`

原因：如果仓库测试版本身发生严重故障，用户仍必须保留一个可以打开、可以重新导入正式版的稳定入口。

因此仓库采用：

```text
我的规则仓库           → Stable
我的规则仓库·测试版    → Test / Candidate
```

同时要求两者 Remote Manager state、收藏、版本记录、搜索历史、导入历史等本地状态默认隔离。

本例外只针对正式版/测试版的同名覆盖规则，不应扩散到其它小程序。

如果“我的规则仓库”以后提供 Local，则本地版使用：

```text
我的规则仓库 本地版
```

Local 与正式/测试都独立并存；仍不再拆 Local Stable/Test。

## 6. 云仓库首页仍只显示一个程序卡片

即使程序拥有正式、测试、本地三个通道，云仓库首页仍只显示一个主程序入口。进入二级版本页后再选择对应通道。

```text
云仓库首页
  ↓
一个程序卡片
  ↓
版本中心
  ├─ 正式版（远程）
  ├─ 测试版（远程）
  └─ 本地版（可选）
```

多通道不能以多个并列卡片污染首页。

## 7. UI 必须明确覆盖与共存语义

对于普通小程序的版本中心：

- 明确提示“正式版与测试版同名，互相覆盖”。
- 明确提示“测试异常时重新导入正式版即可恢复”。
- 如果存在 Local，明确提示“本地版使用‘规则名 本地版’，可以与正式/测试版同时保留”。
- 不得把正式版/测试版描述成可同时安装。
- 版本排序固定为：正式版 → 测试版 → 本地版。
- Test 基础版本不得低于 Stable；Local 展示派生基线，不用“更高/更新”措辞。

对于“我的规则仓库”：

- 明确提示正式版与测试版可以同时保留。
- 说明这是为了自举恢复与故障兜底。

## 8. 发布检查

发布多通道程序前必须检查：

1. 开发前已重新读取长期三文档；涉及版本通道时已继续读取本专项规范和版本谱系规范。
2. 根 manifest 只存在一个主程序入口。
3. `channels.json` 中各通道引用路径/构建元数据真实存在。
4. 普通小程序 Stable/Test 的 `name` 与主程序名完全一致。
5. 普通小程序 Stable/Test 最终导入 Shell 内真正的 `title` 完全一致。
6. “我的规则仓库”测试通道使用独立名称。
7. Local（如有）名称严格为 `<主程序名> 本地版`。
8. Local 不再拆正式版/测试版。
9. Local 最终规则已确认不含私人 GitHub 和其它隐私信息。
10. 正式版 / 测试版 release、build、缓存键、Remote state 不串线。
11. Stable 远程文件不被 Test 原地覆盖。
12. Test 基础版本不低于 Stable；正常向前开发时 Test 使用下一目标版本。
13. Stable 晋级后，下一轮 Test 已先 rebase 当前 Stable，不丢 Stable 已有能力。
14. Local 已记录自己的派生基线；Local 版本不参与 Stable/Test 新旧排序。
15. 测试失败时，正式版入口仍可从云仓库访问并同名覆盖恢复。

## 9. 禁止事项

- 禁止默认给普通小程序测试版程序名加“测试版”“Test”“Beta”等后缀。
- 禁止为了区分正式/测试通道而制造两个长期并存的普通小程序副本。
- 禁止 Stable 已经推进后，Test 仍长期使用更低的基础版本号。
- 禁止 Stable 晋级后，下一轮 Test 继续从旧 Stable release 派生而漏掉正式能力。
- 禁止把 Local 修订号当成比 Stable/Test 更高的产品版本。
- 禁止本地版继续拆“本地正式版 / 本地测试版”。
- 禁止本地版包含私人 GitHub 地址、用户名、Token、Cookie、开发机路径等隐私。
- 禁止把只负责安装远程业务的本地 Shell 冒充“本地版”；Local 必须是业务代码完整内置。
- 禁止只修改 `channels.json` 的展示名，却忘记最终导入 Shell 内 `title`。
- 禁止测试版故障后要求用户手工删除程序再重装；优先利用同名覆盖恢复。
- 禁止让普通小程序测试通道破坏正式版在云仓库中的恢复入口。
- 禁止用旧对话记忆代替开发前读取当前 GitHub 长期三文档。

本规范属于长期发布约束。后续任何支持 Stable/Test/Beta/Dev/Local 的程序都必须先遵守本文件，再设计具体通道实现。
