# Incident: 列表媒体契约与详情重查错源

日期：2026-08-23

## 现象
- 列表卡片已经带有可播放媒体字段，但点击后为了“拿更完整的数据”再次请求详情。
- 详情接口返回的媒体可能是试看、收费未解锁占位、维护线路或与列表语义不同的源。
- 结果表现为：点击等待明显变长；原本应为完整短视频却只播放 1–3 秒；诊断看起来 HTTP/M3U8 都成功但播放内容错误。

## 汤头条实机案例
- Test15/16 的短视频点击后会重新请求 `/api/MvDetail/detail`，再从详情候选挑 source/preview。
- APK 逆向确认原生 `ShortVideoPlayerActivity` 对 `ListLikeVideoBean` 直接读取 `source_240` 并交给播放器；购买成功后才把购买接口返回 URL 回写到同一个 `source_240` 字段。
- 因此短视频列表对象的 `source_240` 才是该页面的原生播放契约，详情重查不是正常首选链。

## 规则
1. **先确认原生客户端在当前页面真正消费哪个字段。** 列表页、详情页、短视频页可以有不同媒体契约。
2. 列表记录已经包含原生页面使用的媒体字段时，首选该字段直接播放；不要无条件重查详情。
3. 只有列表媒体字段缺失、过期或明确失败时，才进入详情/备用 Provider 回退链。
4. 收费内容不通过 URL 改写绕过权限；使用服务端按当前访问状态下发的列表媒体字段，购买后再使用购买接口返回的授权 URL。
5. 性能上避免 `点击 → 详情请求 → 多候选 HEAD → 多次 cacheM3u8` 的串行瀑布。能由列表字段确定时，应直接进入播放器交付层。

## 性能配套
- 同一首页的推荐/长视频通常可共享同一份规范化列表，使用短 TTL 会话缓存即可避免 Tab 切换重复请求。
- 缓存仅保存展示/路由必需字段；媒体鉴权 URL 若明确短时效，播放前需按协议判断是否需要刷新，不能无限持久化。

## 回归门禁
- 记录列表媒体字段是否存在、最终是否走列表快路径。
- 对比点击到播放器打开的等待时间。
- 短视频必须检查真实播放器总时长，而不能只看列表的 `duration_str`；服务端元数据显示异常时不要在 UI 强行展示错误时长。
