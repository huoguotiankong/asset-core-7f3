# 我的规则仓库 UI / UX 设计规范

版本：v1.9
适用：`apps/tools/rule-repo/` 及后续同类云端管理型小程序。

## 1. 产品目标

界面不追求“控件更多”，而追求：

- 用户 1 秒内知道自己在哪、现在是什么状态、下一步能做什么。
- 首屏优先展示高频任务，不展示 Core、build、schema、revision 等工程信息。
- 一个页面只保留一个明确主目标；次级功能收拢到快捷操作或设置。
- Stable / Test 等版本通道属于产品信息架构，不在首页重复占位。
- 所有状态文案从用户语言出发：`有新版本 / 已记录 / 未导入 / 正式版 / 测试版`。
- UI 改版不能牺牲恢复能力；恢复入口必须比新功能更可靠。
- 以海阔实机截图为最终判定依据，代码层“看起来整齐”不能代替真实手机上的密度、截断和触控体验。

## 2. 视觉层级

每个主要页面固定最多四层：

1. Hero：页面身份和当前最重要状态。
2. Primary Navigation / Primary Action：当前页面最常用入口。
3. Main Content：程序、版本、搜索结果或更新列表。
4. Secondary / Advanced：设置、工程信息、诊断与低频操作。

禁止在同一层重复放置同义入口。若一张卡片本身已经是明确的一键主操作，不再在卡片下面重复放一个同义按钮。

## 3. 海阔组件使用约定

结合 Hiker Gallery 实机组件能力，统一优先级：

- `avatar`：首页程序主行与版本主行；利用右侧短 `desc` 显示彩色状态，名称/版本与状态处于同一视线层。当前 Test 的目标程序列表优先使用该组件。
- `rich_text`：紧邻程序/版本主行显示最多 3 个蓝色标签和一行弱摘要。只承担展示语义，不模拟按钮或复杂布局。
- `icon_1_left_pic`：Hero 及搜索/更新等需要两行普通描述的兼容列表；不再作为首页目标程序卡的唯一组件。
- `movie_1_left_pic`：仅在确实需要大封面视觉时使用，不作为普通程序列表默认组件，避免图标过大导致页面显得像影视列表。
- `icon_5`：五项主导航。
- `icon_small_4`：四项统计入口；数字作为主视觉时优先使用仓库内版本化、独立 URL 的静态 SVG，禁止把动态 data-URI 当正式关键视觉。标题始终保留“状态 + 数字”兜底。
- `icon_small_3`：排序、分类筛选、同步等三项紧凑工具栏。
- `icon_2`：只用于实机已经证明比例合适且无需透明占位的两列关系；当前规则仓库分类默认不再使用它模拟左右树。
- `icon_4`：详情页次级快捷操作。
- `icon_4_card`：设置、更新、数据管理等四宫格动作入口。
- `text_3`：分类页主分类等三列卡片入口。
- `text_4`：四项单行状态卡；已知第二行/desc 在部分布局会裁切，因此状态卡采用“标签 + 数值”单行结构。
- `scroll_button`：只用于明确需要横向滚动的少量筛选；带数量的四项也可能在窄屏溢出，不再假设“四项一定放得下”。
- `flex_button`：主分类、历史词、热门标签等需要在一屏自动换行的轻量入口。
- `text_2`：两个并列主操作或状态组合。
- `text_1`：说明、设置项、状态提示。
- `text_center_1`：空状态与弱提示。
- `blank_block`：分区留白。
- `x5_webview_single`：仅在“局部内容独立滚动 + 固定底部导航”属于硬需求时使用。一个工作台只允许一个；目标设备已证伪 `desc:'float&&top'`，而 `list&&screen-100` 仍可能带动外层结果页。本项目固定壳使用 `desc:'float&&screen-100'`，由网页锁定 `html/body/shell` 高度与双轴溢出，并让首页只有程序列表滚动。

普通页面禁止通过大量 HTML 字符串模拟 UI；只有明确需要富文本时才使用 `rich_text`。规则仓库固定底栏单工作台是受控例外：首页、分类、搜索、详情、更新、设置和记录统一在同一 DOM 内切换，必须有结构测试、桥接边界和实机截图门禁。

## 4. 首页规范

首页默认结构：

```text
Hero
单行横滑主分类：全部 / 视频 / 漫画 / 网盘 / 工具 / 聚合
四项数字统计卡：可靠文本数字，不依赖图片解码链
重要状态提示（仅有更新时显示）
我的程序标题 + 搜索入口
排序 / 分类筛选 / 同步
程序主行 + 标签摘要 + 薄分隔
固定底部导航（长列表只在上方工作区滚动）
```

“继续使用”不常驻占据首屏；最近使用通过程序排序、活动记录或搜索进入。目标是让首屏首先形成统计、状态和主列表关系，而不是在程序库前插入第二套程序入口。

首页不直接展示：Core、build、schema、revision、Remote Module、Manager 等工程术语。

## 5. 程序卡片规范

首页程序卡采用两层原生项，视觉上组成一张信息卡：

```text
avatar：图标 | 名称 + 版本 | 右侧状态
rich_text：最多 3 个标签
           分类/运行方式/收藏等一行弱摘要
```

多版本程序：

```text
avatar：图标 | 名称 + 聚合版本 | 版本中心
rich_text：分类 / 管理 / 版本
           正式 / 测试 / 本地统一管理
```

实机优先保证：图标不过大、名称/版本第一眼可读、右侧状态不被描述截断、标签摘要总高度可控。若 `avatar` 右侧富文本在目标设备不兼容，必须回退为短纯文本状态，不得让关键状态消失。

标签最多 3 个，作为弱信息层；不得追加可横向溢出的独立 chips，也不得把 4 个以上标签塞进主标题。

## 6. 详情页规范

普通程序：

- Hero：名称、版本、状态、分类。
- 信息区：云端版本 / 本地版本 / 大小 / 类型 / 更新时间，使用紧凑只读信息行。
- 标签 + 一段程序说明，避免多段技术解释。
- 主操作：`打开程序` + `更新到最新版 / 导入覆盖`。
- 五项次操作：收藏、检查更新、活动记录、备份、更多。
- 最近使用仅在有记录时显示。
- 低频工程操作不得抢占主视觉。

### 6.1 多版本程序 / 版本中心

多版本页面是**版本选择决策页 + 恢复入口**，不是技术版本列表。

固定结构：

```text
Hero：程序名 + 一句话说明版本定位
正式 / 测试 / 本地版本信息行
打开程序 + 检查版本
正式版 avatar：版本 + 右侧“稳定推荐/当前运行”
测试版 avatar：版本 + 右侧“抢先体验/当前运行”
本地版 avatar：版本 + 右侧“独立安装”
每张版本卡下方一行亮点摘要
收藏 / 同步 / 活动记录 / 设置 / 返回仓库
恢复机制：一句话说明测试版异常时怎么恢复
```

设计要求：

- 正式版永远先展示，并标识“推荐”。
- 测试版标识“抢先体验”，不能在视觉上压过正式版。
- 当前正在运行的通道应明确标记“当前运行”。
- 用户不需要理解 build 才能做决定；build 只允许出现在高级信息或发布追踪中。
- 版本卡片本身就是主 CTA，整卡点击直接导入；卡片描述必须明确写出“点击导入”，不再额外堆叠同义“导入版本”按钮。
- 正式 / 测试版本说明使用用户语言，避免堆叠 Stable / Candidate / Remote Module 等英文工程术语。
- 页面只保留一段恢复说明，不堆叠“本版特点 / 本轮重点 / 版本策略 / 架构说明”多段文字造成大面积留白。
- “我的规则仓库”作为自举恢复例外，正式版和测试版使用不同程序名，可同时保留。
- 其他普通小程序正式版与测试版保持同名，通过海阔同名覆盖切换；测试失败时重新导入正式版恢复。
- 版本元数据必须缓存；网络异常时优先使用最近一次有效版本信息。
- 对“我的规则仓库”必须保留内置恢复元数据兜底，避免云端版本描述暂时不可读时连恢复入口也丢失。
- 版本页自身的 `channelMeta / fallback` 必须由当前 release 自包含，不允许依赖旧版本模块仍留在运行时环境。
- 程序命名语义遵循 `docs/HIKER_RULE_NAME_CHANNEL_POLICY.md`。

## 7. 分类与搜索规范

- 分类页是分类关系页。当前 Test 默认使用 35/65 双栏树：左侧纵向主分类，右侧显示对应子分类；点击“全部视频 / 短剧”等目标行后，在该行下方展开匹配程序卡，点击程序卡才进入同工作台详情。
- 禁止用连续 `icon_2/text_2` 成对结果伪造双栏树，也禁止透明 SVG 补齐左右列；这两种做法已在实机形成灰色按钮墙或破图。
- 双栏树属于固定底栏单工作台；五项导航、分类树和内联程序卡共处同一个锁定视口。分类目标行只做展开/收起，不创建新的海阔页面；若 X5 不可用则回退为主类/子类纵向任务结构，优先保证功能可达。
- 选择主分类后清理旧子分类/标签；选择子分类后同步首页分类状态并把首页状态筛选重置为“全部”。
- 标签、运行方式、排序、批量管理继续由首页紧凑工具栏、搜索或后续高级入口承担，不塞进分类树。
- 搜索页四个带数量的常驻范围使用等宽单行卡或可换行入口，不使用可能生成 `>` 的长标题 `scroll_button`；低频“远程 / 本地”收进运行方式选择。
- “清空最近搜索”属于记录管理动作，必须放入更多菜单/工具入口，不得与历史关键词使用同款搜索 chip；热门标签数量受控，避免再次形成灰色胶囊墙。
- URL 参数进入搜索页时必须先安全 `decodeURIComponent`，禁止 `%E6%...` 编码串直接展示给用户。

## 8. 设置与更新中心规范

设置页优先采用动作分组，而不是长篇说明列表：

```text
同步与更新：自动检查 / 离线缓存 / 立即同步 / 版本更新
数据管理：备份 / 恢复 / 活动记录 / 清理数据
关于：版本信息 / 产品说明 / 活动记录 / 诊断信息
```

- `icon_4_card` 用于四宫格高频动作，解释文字压缩为一个当前策略摘要。
- 清理动作通过二级选择收拢，禁止首页常驻四个“清空”按钮。
- 工程信息仅在诊断入口内展示。

更新中心只承担两类核心任务：

1. 当前程序自身的版本更新 / 回退。
2. 云端程序目录同步。

没有待更新时直接给出清晰空状态，不长期列出“已经是最新版”的程序。

## 9. 状态与反馈

- 页面加载：使用 `showLoading / hideLoading`。
- 成功：短 Toast，不长篇解释。
- 失败：说明用户能采取的下一步操作，不直接把技术堆栈作为主界面文案。
- 空状态：说明为什么为空和可以做什么。
- 更新：先验证再切换；失败不覆盖当前有效版本。
- 网络失败：优先旧缓存兜底，不直接白屏。
- 同步：禁止“先清最后有效缓存，再联网读取”。必须先获取并校验新数据，成功后再替换旧缓存。

## 10. 发布要求

任何 UI 重构均遵循：

```text
Candidate/Test
→ Release Guard
→ 海阔实机关键路径验证
→ Stable Promotion
```

正式版不直接承接未经实机验证的大规模 UI 改动。

固定底栏候选还必须确认：长列表滚动时只有程序区移动、Hero/工具栏/五栏不移动、工作台只有一个 X5、没有横向漂移、分类原地展开、内部路由不会增加海阔页面层级、桥接业务动作与恢复链正常。

## 11. 设计审查清单

每轮提交前检查：

- 首屏是否有重复功能？
- 首页是否明确出现数字统计、右侧状态和标签摘要三层关系？
- 最重要操作是否一眼可见？
- 是否把工程信息暴露给普通使用者？
- 程序图标是否过大、单卡是否过高？
- `avatar` 右侧状态在目标设备是否可见；不支持富文本时是否仍有纯文本退路？
- 是否存在超过两行的程序卡片信息堆叠？
- 多版本页是否让用户无需理解技术术语就能选对版本？
- 正式版是否明显优先于测试版？
- 版本卡片本身是否明确可点击导入，而不是再堆重复 CTA？
- 当前运行版本是否明确？
- 测试版异常时，正式版是否仍能独立完成恢复？
- 版本元数据断网时是否有缓存 / 内置兜底？
- 当前 release 是否自包含所依赖的公共函数，而不是依赖旧缓存残留？
- 分类高级选项是否默认收起？
- 分类页是否真正表达主类/子类关系，并由目标行原地展开程序卡，而不是两列灰色按钮墙、破图占位或每点一次创建新页面？
- 首页长列表滚动时，五项导航是否仍固定在底部？
- 页面是否只能纵向滚动，且分类条/最近使用之外没有整页横向漂移？
- 网页桥 URL 的 `rule` 是否为目标设备可识别的原始规则名，而非 `%E6%...` 编码串？
- 网页桥 `parseLazyRule` 是否由完整 HTTPS 基址生成动作，并在解析后把导入口令、提示、复制、确认与合法 URL 明确分流，而不是复用 `#noLoading#` 或把未知文本当网址？
- 动态动作加载 `ruleRepoCore` 时是否显式携带当前原始规则名，并在子页面不可用时通过当前版本 Bootstrap 恢复 Core？程序/版本导入、备份和诊断必须作为同一动作桥回归组一起验证。
- 单工作台是否严格保持“一页一个 X5、内部视图同 DOM、只有真实打开/导入/更新跨出工作台”的边界？
- 搜索 URL 中文参数是否正确解码？
- 设置页是否仍存在大段说明和重复清理按钮？
- 是否有无意义 Emoji / 符号混排？
- 各页面导航、标题、留白是否一致？
- 空状态、错误状态、加载状态是否完整？
- 深色/浅色主题下是否依赖硬编码背景色？
- 新功能是否增加了不必要的页面层级？
- 所有同步是否遵守“新数据成功后再替换旧缓存”？
- 是否仍可安全回退？
