# 事故：短视频错误复用长视频完整性校验

日期：2026-08-23  
来源：汤头条 Test12 → Test13 实机回归

## 现象
- 短视频列表能够正常返回并显示封面，但点击后提示“未找到完整可播放线路”。
- 诊断中短视频标称时长仅 2 秒，HLS 实际约 1 秒，旧 PlaybackAdapter 因 `ratio=0.5` 判定为可疑短源。
- 同一详情还存在 `source_origin` 的真实 `.mp4` 地址，但通用播放探测把它误送入 M3U8/密文解析，最终出现“m3u8 密文不是合法 HEX”。

## 根因
短视频和长视频的播放语义不同：
- 长视频需要用元数据标称时长与 M3U8 总时长交叉校验，过滤维护片、试看片和不完整线路。
- 1–2 秒、十几秒的短视频受编码舍入、EXTINF 粒度影响明显，不能使用相同的比例阈值。
- 已明确为 `.mp4` 的 `source_origin` 应作为直接媒体地址处理，不应先假设 HLS/M3U8。

## 固定规则
1. **短视频播放必须与长视频完整性校验分离。**
2. 免费短视频优先顺序：
   - 已验证的直接 MP4 / `source_origin`；
   - 短 HLS；
   - 官方 preview。
3. 短 HLS 可以做 HTTP/格式有效性检查，但默认不使用长视频“实际时长 / 标称时长比例”阈值。
4. 长视频仍必须保留完整性校验，不能因为短视频放宽而一起取消。
5. 媒体类型优先依据明确字段、响应 Content-Type、真实内容和扩展名综合判断；不要把所有 URL 统一扔进 M3U8 解密器。
6. 收费/试看内容仍以业务权限模型为准，播放兼容层不得通过删试看参数、改时长参数等方式越过业务授权。

## 汤头条 Test13 对应修复
- 新增 `playShortById` 短视频专用入口。
- 免费短视频优先 App 详情的 `source_origin .mp4` 直接交海阔播放器。
- 无 MP4 时再走短 HLS，`expectedDuration` 为空，避免长片比例规则误杀。
- 收费短视频仅使用 App 下发的官方 preview，不自动调用汤币消费接口。
- 新增 `ttt_last_short_play` 诊断，记录最终使用 direct-mp4 / short-hls 及来源。
