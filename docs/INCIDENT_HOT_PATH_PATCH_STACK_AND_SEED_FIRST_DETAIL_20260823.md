# 海阔热路径性能：补丁栈、重复索引请求与 Seed-First Detail — 2026-08-23

## 事故来源
麻豆传媒 Test8–Test10 实机。

## 实机现象
- Test8 为了研究播放免嗅，在详情 `setResult()` 前同步追踪多个 player/iframe/nested-player，导致详情明显变慢。
- Test9 将多跳收敛成“一次详情请求”，但用户实机仍确认详情偏慢；原因是**详情本身仍被强制网络请求阻塞**。
- 分类内容页每次切换同组小分类时，旧实现会先重新抓首页、重建 14 个大分类/373 个小分类索引，再抓目标分类内容；在源站本身响应较慢时，切换体验被重复请求成倍放大。
- Test9 Release 已叠加 9 个历史模块/补丁。即使 `require` 有缓存，热点页面仍承担不必要的加载、覆盖和维护复杂度。

## 根因结论
页面性能不能只看“单个请求是否减少”。需要把热路径拆成：

```text
页面壳/已知 seed
→ 必需主数据
→ 可选扩展数据
→ 媒体协议研究/诊断
```

列表卡已经持有标题、封面、摘要时，详情页再为了同一批基础字段同步请求整页 HTML，是可避免的重复工作。分类树已经解析成功后，同级切换再重新请求首页只是重新构造同一索引，也属于可避免的重复工作。

## 固定规则
1. **Detail Seed First**：列表/搜索/收藏/历史已经拥有 `id/url/title/cover/summary` 时，详情首屏优先直接使用 seed 渲染；标签、相关推荐、完整作者资料、媒体协议等扩展字段按需加载，不能阻塞首屏。
2. **分类索引与分类内容分离**：分类树/导航树解析成功后保存小型结构化 `CategoryModel`；同级分类切换不得重新请求首页/菜单来重建索引。
3. **缓存解析结果，不缓存大型 HTML**：允许有界保存 `CategoryModel`、最近 Feed 的 `CardModel[]`、少量 DetailSeed；禁止为了加速重新把完整 HTML 写入私有 `setItem`。
4. **热路径一次请求预算**：一个用户点击如果理论上只需要一个业务页面请求，就禁止默认串行 `fetch → request → fetchCodeByWebView → player`。Fallback 必须按失败层显式触发，不得全部堆在首屏前。
5. **Stale 优先于长时间空白**：最近成功的结构化 Feed 可在短 TTL 内直接显示；网络刷新失败时允许展示 stale 数据 + 状态提示，而不是让页面一直加载。
6. **补丁链必须定期收敛**：同一 Test 连续叠加多层覆盖后，如果已出现多次性能/行为回归，应新建性能 rebase，保留最后实机可用能力但压缩为少量稳定模块。不要无限追加第 N 个覆盖补丁。
7. **协议研究不得污染产品首屏**：播放器 API、加密参数、iframe 链、WebView 诊断属于 Playback/Protocol 研究任务；除非结果已经缓存/确定，否则不得在详情首屏同步执行。
8. **首屏完成定义包含时间预算**：详情、分类、账号、搜索等页面不能只以“最终能出来”为完成；应记录冷启动、缓存命中、网络失败时的用户等待边界。

## 麻豆传媒 Test10 落地
- Release 从 Test9 的 9 层补丁收敛为 `Core + Runtime + PerformanceRuntime` 三个模块。
- 分类树保存为有界 JSON；分类中心和同组切换只读取本地索引，不再重新抓首页。
- 最近 6 个分类页缓存最多 30 张解析后的卡片，20 分钟内回切直接本地渲染。
- 列表卡把标题、封面、摘要作为 DetailSeed 放进路由；正常详情首屏零网络请求。
- 标签/相关推荐改为用户显式“加载扩展信息”后再请求详情。
- 热路径普通请求仅保留一次约 6.5 秒预算，不再自动追加第二套 transport/WebView。

## 发布门禁
今后出现“详情/分类/我的/搜索越来越慢”时，先检查：
- 是否在首屏同步做 P2/P3 数据；
- 是否同一点击重复请求索引/详情；
- 是否存在 N+1；
- 是否补丁栈已经需要 rebase；
- 是否可以用结构化 seed/stale cache 立即渲染。

若其中任意一项成立，优先修架构热路径，不继续通过增加 timeout、更多 fallback 或更多 WebView 来掩盖性能问题。
