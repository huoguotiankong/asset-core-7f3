# Incident：Local-First 版本目录“检查版本”未刷新权威目录（2026-08-25）

## 症状
- 正式版规则仓已经能看到某程序的新 Test 元数据，但 Local-First 测试版程序详情仍长期显示旧版本。
- 用户点击“检查版本”后没有得到新版本，反而出现前台长时间卡住。

## 根因
1. 正常详情页按 Local-First 设计只读本地统一版本目录，这是正确的热路径优化。
2. 旧“检查版本”按钮并没有刷新该权威目录，而是重新进入完整 Runtime，并执行 `findById(id,true)` / 安装状态检查，再读取原有本地版本信息。
3. RC24 轻同步的统一版本目录只通过 Raw 单路 `batchFetch`；Raw 单路失败时会静默保留旧目录，没有 GitHub Raw / jsDelivr 镜像兜底。
4. 因而形成“按钮名叫检查版本，但实际不检查版本目录”的产品与实现错位。

## 修复原则
- 正常浏览：继续保持版本详情零网络，只读本地统一目录。
- 用户主动“检查版本”：只刷新统一版本目录，不加载完整 Runtime、不扫描安装状态、不请求每个程序独立 channels。
- 版本目录刷新采用 Raw / GitHub Raw / jsDelivr 多镜像并行；多个有效结果同时存在时选择 revision 最新者，避免 CDN 陈旧值覆盖新目录。
- 刷新成功后写入本地目录并刷新当前页面；失败则明确提示并继续保留现有本地目录。
- 普通“同步”可以继续承担根 manifest / 图标包等工作，但版本目录必须有独立的多镜像兜底，不能把单路 Raw 成功当作前提。

## 禁止回归
- 禁止“检查版本”重新进入完整 Remote/Local Runtime 来做网络探测。
- 禁止“检查版本”只清安装状态缓存而不刷新版本权威目录。
- 禁止在版本详情热路径恢复 N+1 per-app `channels.json` 网络 hydration。
- 禁止单 CDN/单 Raw 结果无版本比较地覆盖本地更新目录。

## 实机验收
1. 打开程序详情应立即显示本地版本，不联网等待。
2. 点击“检查版本”应在短时间内结束。
3. 当云端统一目录有更新时，检查后当前页面应显示新 Stable/Test/Local。
4. 网络失败时应快速返回错误提示，旧本地目录仍可继续浏览。
