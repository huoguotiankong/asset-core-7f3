## 1.2.0-test.7 / Build 2026092208 — 迅雷式动态任务页 + 离线延迟分层

用户实机截图给出一个关键证据：同一条 `FNS-252` 磁链在 **01:51** 的外部调用聚焦页仍停在“正在连接115…”，但同一分钟进入“全部离线任务”后已经显示 `FNS-252 ✅ 已完成`。因此该案例中主要延迟不是 115 后台离线本身，而是 Test6 聚焦页只在首屏 `setResult()` 了一次静态等待壳，后续真实任务状态没有及时同步到页面。

这次必须区分两类“慢”：

```text
小程序侧延迟
= 首屏阻塞 / 提交请求等待 / 任务状态查询 / 页面状态传播 / 文件结果定位

115服务端真实离线耗时
= 任务已经创建之后，115后台从等待/下载到完成的时间
= 受115服务端、资源健康度、种子/缓存命中等影响
```

Test7 只优化小程序侧，不伪造或宣称能加速 115 服务端真实离线速度：

- 外部 magnet 首屏立即显示任务卡，不再只显示静态“正在连接115”；
- 使用海阔官方 `batchExecute()` 做后台提交与分阶段状态查询，首屏不等待这些网络动作；
- 使用 `updateItem()` 原地更新任务卡：`正在提交 → 已提交 → 已建立任务 → 下载中xx%/速度 → 已完成`；
- 轮询按约 `0 / 0.7 / 1.5 / 2.6 / 4 / 6 / 9 / 13s` 错峰执行，任务完成后主动中断剩余检查；
- `add_task_urls` 超时不直接判定失败，因为 115 可能已经受理；后台任务查询继续确认，避免用户重复提交；
- 一旦任务返回 `fileId` 或完成状态，把任务写入本地 ready cache 并自动 `refreshPage(false)` 一次；刷新后直接展开结果目录/视频，视频继续复用 Stable `115Api.player.resolve()`；
- 页面继续显示实际保存目录，保留 `海阔视界 → 云下载/离线下载 → 根目录` 策略；
- 程序名继续固定 `115.简`，同名覆盖并复用原登录/Cookie；
- Stable 1.1.0 不修改。

实机验收重点：

1. 用一个新的、未离线过的 magnet 从 JavDB/磁力君调用；
2. 页面应立即出现任务卡，不能长时间只停在“正在连接115”；
3. 如果115很快完成，任务卡应自动切换为完成并进入文件结果，不再要求手动进入“全部离线任务”；
4. 如果115确实在下载，页面应显示下载状态/百分比/速度（以115接口真实返回为准）；
5. 新任务仍应保存到根目录/海阔视界；
6. 真正服务器端长时间未完成时，页面只能如实显示“115仍在后台处理中”，不能用小程序假装提速。

当前状态：`active-test-dynamic-focus-pending-device-validation`。

- 找不到 `海阔视界` 时才复用/识别 `云下载` 或 `离线下载`；

- Stable 1.1.0 不修改。

实机验收重点：

1. 根目录已存在 `海阔视界` 时，用一个未离线过的新 magnet，115 实际文件必须落在该目录；
2. 临时不存在 `海阔视界` 时，应自动回退到 `云下载/离线下载`，不能优先落根目录；
3. 手动添加离线、失败任务重试和外部磁链三条入口保存位置必须一致；
4. 导入后程序仍叫 `115.简`，既有登录状态继续可用；
5. 进入磁链页不应再出现 `_115CloudCid` 重复声明；
6. Stable 1.1.0 保持不变。

## 1.2.0-test.1 / Build 2026092202 — 云下载目录 + 快速离线结果

用户实机继续反馈 Stable 1.1.0 两个体验问题：

1. 外部 magnet 提交后经常需要手动刷新多次，才能看到任务完成或进入结果；
2. 新离线任务默认落在网盘根目录，而不是 115 自己的“云下载”目录。

源码恢复确认根因：Stable 1.1.0 的 `115Offline` 在外部 magnet、失败重试、手工添加三条链上都把 `addOfflineTaskURIs(..., "0")` 写死，`"0"` 即根目录；新任务提交后也只立即查一次任务列表，没有短时自动追踪，所以 115 后端稍有最终一致性延迟就需要用户手动刷新。

Test 1.2.0-test.1 只覆盖 `115Offline`，Stable 1.1.0 保持不动：

- 优先调用 115 `get_id` 能力读取 canonical 云下载目录，取返回的 `dest_cid` 作为离线 `wp_path_id`；
- 云下载 CID 会本地缓存，并在后续进入离线页时通过当前 115 Client 校验；
- 官方目录解析失败时，仅尝试复用根目录中已存在的“云下载/离线下载”目录；仍失败才临时回退根目录，并在 Test 页面显式提示，便于实机反馈；
- 外部 magnet 提交后进行有上限的短时轮询，不做无限阻塞；
- `fileId` 一旦出现就视为“结果已开始可用”的提前信号，不再只等 `status === 2`；
- 当前磁链页会直接展开任务结果目录中的文件夹和视频；视频点击继续复用原版 `115Api.player.resolve()`；
- 保留 Stable 1.1.0 的 BTIH/URL 查重、结果缓存、失败重试、主片直放、多集选集逻辑；
- 不修改登录/Cookie/扫码、m115 加解密、115 分享、普通网盘文件列表与搜索、直链播放器。

实机验收重点：

1. 用一个未缓存的新 magnet 从 JavDB/磁力君等入口调用 `115Offline?add=`；
2. 页面应显示“☁ 保存到 115 云下载”及实际 CID，而不是根目录回退警告；
3. 新任务出现/返回 `fileId` 后，不应再依赖连续手动刷新多次；
4. 当前页应尽快出现 `📂` 结果目录和 `▶` 视频项，点击视频可直接播放；
5. 115 网盘实际文件位置应位于云下载目录；
6. 重复调用同一 magnet 仍应查重，不产生重复离线任务。

## 基线与协议事实

基线来自用户上传的 `115.简.hk小程序.zip`，原规则为单文件 `rule.json`。原实现已具备：

- 115 Cookie / 扫码登录；
- 文件列表与全盘搜索；
- 115 分享；
- 离线任务；
- `magnet / ed2k / http(s)` 离线添加；
- 个人网盘文件直链解析与播放。

已确认：

- `addOfflineTaskURIs()` 使用 `https://lixian.115.com/lixianssp/?ac=add_task_urls`；
- `listOfflineTask()` 的 `file_id` 映射为任务结果 `fileId`；
- `wp_path_id` 映射为 `dirId`，它是任务结果的父目录；
- 原 `player.resolve()` 能通过 pickcode / fileId 取得 115 直链并带 UA/Header 播放。

## 对外磁链调用协议

其它小程序调用 115 播放 magnet 的正式入口固定为：

```js
"hiker://page/115Offline?rule=115.简&page=fypage&add=" + encodeURIComponent(url)
```

原版旧“复制调用”里的：

```js
"hiker://page/115Search?rule=115.简&page=fypage&kw=" + encodeURIComponent(url)
```

**禁止用于 magnet。** 用户实机已证明它只会把整条 magnet 当普通网盘搜索关键词，结果为 `共0条 / 无结果`。

首页真实输入分流：

```text
115 分享链接
→ 115Share?sc=

magnet / ed2k / HTTP(S)
→ 115Offline?add=

普通关键词
→ 115Search?kw=
```

## Stable 1.1.0 磁链播放链

```text
其它小程序传 magnet
→ 115Offline?add=
→ BTIH / URL 查重
→ 当前任务聚焦
→ 已存在则复用，不重复离线
→ 新任务才提交到 115 离线
→ 完成后优先 task.fileId
→ fileId 是视频：直接进入原版 player.resolve
→ fileId 是目录：受控扫描视频
→ 过滤 sample / preview / trailer / 试看 / 预告 / 花絮 / 广告等噪声
→ 单一明显主片：直接播放
→ 多集 / 多段：进入 115OfflineResult 选集
→ 播放结果缓存复用
```

扫描边界：最多递归 4 层、最多约 500 项，避免大目录拖死页面。

- 多集/多段命名识别优先进入选集。

## 2026-09-21 实机验证结论

### 原版基线

用户实机确认：原版首页直接输入 magnet 可成功添加 115 离线任务。

### 原版完成任务问题

用户实机截图确认原版完成任务点击后：

```text
meyd-553 完成任务
```

多集选集逻辑已经过静态/mock 回归并随 RC1 冻结进入 Stable；后续如出现特殊命名误判，继续在 Test/Candidate 小步修复，不原地覆盖 Stable。

## 后续其它小程序接入规范

其它带 magnet 的小程序只依赖这一条稳定契约：

```js
function playBy115(url) {
    if (!url) return "toast://未获取到磁力链接";
    return "hiker://page/115Offline?rule=115.简&page=fypage&add=" + encodeURIComponent(url);
}
```

调用方不得直接依赖 115Api、fileId、离线接口或播放器内部实现。115 内部以后升级时必须继续兼容 `115Offline?add=`，避免批量修改所有上游小程序。
